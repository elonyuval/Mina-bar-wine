# Local business site

A one-page Hebrew site that makes a small venue look like it hired a studio.
Static HTML/CSS/JS, no framework, no build step — the owner can host it free
and you can hand-edit it a year from now without reinstalling anything.

The reason this skill exists: the *code* is the easy part. What burns time is
Hebrew bidirectional text quietly reversing prices and hours, logos that arrive
as a screenshot instead of a file, and a deploy that silently needs a human to
click one toggle. Those are solved below — don't rediscover them.

## Start by asking for the raw material

Owners rarely have a brief. They have a phone full of screenshots. Ask for
exactly this, as a checklist they can work through — and say that photos matter
most, because a venue is sold with the eyes:

> **תמונות** — 8 בערך. אחת רחבה לראש העמוד (חזית/אווירה), אחת אנכית, ו-6 לגלריה. מהאינסטגרם זה מצוין.
> **לוגו** — הקובץ המקורי. אם אין, צילום מסך גם עובד.
> **תפריט / מחירון** — צילומי מסך. שלח כמה שנוח, אני אצליב ביניהם.
> **פרטים** — כתובת, טלפון, שעות פתיחה לכל יום.
> **הזמנות** — הקישור המדויק (Ontopo/Tabit/Calendly), או טלפון/ווטסאפ.
> **רשתות** — אינסטגרם/פייסבוק.
> **ביקורות** — העתק-הדבק מגוגל, כולל הדירוג ומספר הביקורות.

Decide these four before writing code, since each changes the structure:
page shape (one-pager is right ~90% of the time), languages (Hebrew-only unless
there's a real tourist audience), how people book, and where it will be hosted.

Then start building with whatever has arrived. Don't block on the full set —
the layout can go up with placeholders and the content can land in batches.

### Working through screenshots

Batches arrive over several messages and overlap heavily. Two habits pay off:

**Transcribe as they arrive, into a scratch file, before continuing.** Context
gets summarized in long sessions; a `menu-batch-N.md` on disk does not.

**Treat overlap as free verification.** When a later screenshot repeats a
section you already typed, cross-check it with a script instead of by eye:

```python
m = re.search(r"title: '" + re.escape(group) + r"',\s*items: \[(.*?)\n        \],", src, re.S)
got = [int(x) for x in re.findall(r"price: (\d+)", m.group(1))]
print('✓' if got == expected_from_screenshot else '✗', group, got)
```

Catching one wrong price this way is worth more than the minute it costs. It
also catches truncation — a list cut off by the screen edge looks complete
until a second screenshot shows four more items below the fold.

## Architecture

```
index.html              all page content + JSON-LD for Google
assets/css/style.css    design tokens + components
assets/js/menu-data.js  ← the only file the owner ever edits
assets/js/main.js       nav, menu rendering, scroll behaviour
assets/img/             generated by the scripts below
.nojekyll               so GitHub Pages serves files verbatim
```

The split matters: prices change monthly, everything else almost never. Keeping
the menu as a plain data file means a non-developer can update it without
touching markup, and you can regenerate the whole menu section from one edit.

Copy `assets/style.css`, `assets/main.js`, and `assets/menu-data.js` from this
skill as your starting point, then adapt the palette and content.

Have `main.js` skip any category whose groups are all empty. Menus arrive in
pieces, and a category that renders nothing until it has content lets you commit
a stub for a section you haven't been sent yet without it showing up as an empty
tab on the live site.

## Structure the content for a visitor, not for the source

The owner's existing menu system is organized for the kitchen or for whatever
booking platform they use. It's usually wrong for a website, and copying it
faithfully is a disservice. Real examples worth generalizing: a booking platform
filed 58 wines and 20 spirits under one "alcohol" tab, where the wine list
buried everything else — split them. It also filed desserts under alcohol —
move them to the food menu, where people look.

Reorganize when a visitor would be better served, and say plainly in your
summary what you changed and why, so the owner can push back.

## Hebrew and RTL

This is where sites like this actually break, and the failures are invisible
until you look at a rendered screenshot — the HTML source reads perfectly.

Set `<html lang="he" dir="rtl">` and lay out with logical properties
(`margin-inline-start`, `inset-inline`, `padding-inline`) rather than
left/right, so the layout follows direction instead of fighting it.

The dangerous part is bidirectional text. A neutral character — a comma,
a hyphen, a bullet — sitting between a number and Hebrew, or between two
numbers, gets absorbed into the wrong run and reorders on screen:

| Written | Renders as | Fix |
|---|---|---|
| `18:00 — 24:00` | `24:00 — 18:00` | `<bdi dir="ltr">18:00 – 24:00</bdi>` |
| `4.9 ב-Google · 52 ביקורות` | scrambled | `<bdi>Google</bdi>` |
| `קרל פופר 7, נתניה` | comma jumps left | `קרל פופר 7&rlm;, נתניה` |

The rule to carry: **any Latin word or number range embedded in Hebrew needs
isolation** — `<bdi>` around it, or `&rlm;` after a trailing digit.
`references/rtl-hebrew.md` has the full catalogue.

Verify by rendering and *looking*, not by reading source. Screenshot the page
with Playwright and read the image — every BiDi bug found in practice was found
this way and would have survived any amount of source review.

## Assets

Owners send screenshots, not assets. Two scripts do the conversion:

**`scripts/extract_logo.py`** — turns a logo screenshot into transparent PNGs.
A logo photographed off Instagram is light marks on a solid brand-coloured
background. Alpha derived from luminance recovers clean, anti-aliased edges,
and recolouring gives you a dark version for light headers and a white version
for dark footers. It also prints the sampled background colour — use that as
the site's brand token instead of guessing a hex from looking at the image.

```bash
python3 scripts/extract_logo.py logo-screenshot.jpg assets/img/
```

**`scripts/build_images.py`** — crops the photo set to every size the page
needs (hero, portrait, square gallery tiles, social preview, favicon):

```bash
python3 scripts/build_images.py --hero cheers.jpg --portrait shelf.jpg \
    --gallery a.jpg b.jpg c.jpg d.jpg --out assets/img/
```

Both need Pillow (`pip install Pillow`).

Where do the files land? Images pasted into a conversation are usually written
to disk by the harness even though they read as inline images — look for an
uploads directory before telling the user you can't use them. Getting this
wrong wastes a whole round trip.

A photo behind hero text needs a scrim, or white type on a bright patch becomes
unreadable. Use two stacked gradients — one along the text axis, one from the
bottom — rather than a flat overlay, which dulls the whole photo.

## Publishing

GitHub Pages, free, on a public repo. **Pages cannot be enabled programmatically**
— `POST /repos/{owner}/{repo}/pages` is blocked for Actions' `GITHUB_TOKEN` and
for most sandboxes. A workflow using `actions/configure-pages` with
`enablement: true` fails with *"Resource not accessible by integration"*. Don't
ship that workflow; it just emails the owner about failures it can't fix.

Serve straight from the default branch instead, and give the owner precise
instructions — the branch dropdown defaults to `None` and the Save button is
easy to miss, which is the usual reason "I already did it" and `has_pages:false`
are both true:

> Settings → Pages → Source: **Deploy from a branch** → Branch: `<branch>` → `/ (root)` → **Save**
> Confirmation looks like: *"Your site is live at https://USER.github.io/REPO/"*

Verify with the API (`has_pages`) and by checking that the
`pages build and deployment` run succeeded. A 401 or 404 right after enabling is
normal — the first build takes a minute. Say so instead of debugging a
non-problem.

## Preview link

Owners want to see it before the domain exists. Publish a self-contained copy as
an artifact with `scripts/build_preview.py`, which inlines the CSS and JS,
embeds images as data URIs, swaps the map iframe for a linked card, and falls
back to system fonts — a strict CSP blocks every external host.

```bash
python3 scripts/build_preview.py --out preview.html
```

**The artifact wrapper supplies its own `<html>` with no `dir`.** Extracting
just the `<body>` throws away `dir="rtl"` and the entire page silently flips to
LTR. The script sets direction from inside the content; if you hand-roll this,
don't forget it.

## Finishing

Before handing over: render desktop and mobile and actually look at both; check
`document.documentElement.scrollWidth === clientWidth` so nothing scrolls
sideways; confirm no console errors and no broken images (prime lazy images by
scrolling first, or you'll chase phantom failures).

Add JSON-LD (`Restaurant` / `BarOrPub` / `LocalBusiness`) with address, phone,
hours, rating, and `acceptsReservations`. For a local venue this is most of the
SEO that matters — it's what puts the hours and stars in Google's result.

Write the README in the owner's language, and tell them the one file to edit for
prices.
